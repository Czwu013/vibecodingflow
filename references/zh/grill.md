# 立项追问：把范围问清楚再动手

目录：1 怎么问 · 2 答案落到哪里 · 3 第一轮：目标与范围 · 4 第二轮：流程、数据、尺子 · 5 第三轮：节奏与风险 · 6 工具 / 网站补充 · 7 游戏补充 · 8 收尾检查 · 9 反模式

## 1. 怎么问

立项时最贵的错误是"范围没问清就开做"。DESIGN 不是让人对着空表格填，而是 AI 追问、人只需回答"同意 / 不同意"。

- 装了 `grill-me` skill 就用它来跑追问的机制；没装就按下面的规则自己来。
- **分轮提问。** 一轮 = 现在就能问的所有问题（不依赖尚未回答的问题）。依赖前面答案的题放到下一轮。
- **每题带推荐答案**，措辞要让人回"同意"就等于采纳。
- **事实自己查，不问人。** 现有代码、技术栈、依赖版本、类型预设里的验收基准，都先自己看。决定才问人。
- **结束条件：** 没有未展开的分支，且人明确说"共识达成"。在此之前不写 plans，不写代码。
- 按规模控制深度：M 档只问第一、二轮；L 档三轮都问，并在写计划时对技术方案再追问一次。

## 2. 答案落到哪里

每个答案马上写进对应位置，不要攒到最后：

| 追问内容 | 落到 |
| --- | --- |
| 给谁用、解决什么问题、一句话定位 | DESIGN §2 概述 |
| 核心流程 / 核心循环 | DESIGN §3 |
| 做 / 不做、完成标准 | DESIGN §4 MVP 范围 |
| 参数、可调项 | DESIGN §5 |
| 每个维度 4 分长什么样 | DESIGN §6 验收基准 |
| 技术选型、里程碑顺序 | DESIGN §7 |
| 开工前的批判性问题（回退、调试信息、合规） | DESIGN §0 |
| 还没定的、先按默认走的 | DESIGN §9 待决问题（标"假设"） |
| 真正的取舍和放弃了什么 | DECISIONS.md |

## 3. 第一轮：目标与范围（所有 M / L 任务）

1. **使用者与场景：** 谁用、在什么情况下用？（推荐：先只服务一类用户）
2. **要解决的问题：** 不做这个会怎样？一句话说清。
3. **最小可用版本里必须有的行为：** 3–7 条，每条写成"用户做什么 → 看到什么"。
4. **明确不做：** 账号、多人协作、云同步、支付、多语言、后台管理等，逐项确认是否排除。（推荐：能排除的先全排除）
5. **完成标准：** 做到什么算这一轮完成？写成可勾选的清单。

## 4. 第二轮：流程、数据、尺子

6. **核心流程：** 用户反复做的那件事，一步一步是什么？
7. **数据从哪来、存在哪：** 手输、导入、接口？内存、本地存储、文件、数据库？刷新后要不要保留？
8. **演示数据怎么标识：** 怎样让它一眼和真实数据区分，不混进去？
9. **技术选型：** 已有项目沿用；新项目给 2 个候选和理由。（推荐：AI 能完整读懂和改动、依赖最少的）
10. **验收基准：** 每个维度 4 分长什么样？有类型预设时，把预设的基准当推荐答案，让人改。
11. **回退办法：** 改坏了能不能一键退回？（推荐：git，每个任务一次小提交）

## 5. 第三轮：节奏与风险（L 档必问，M 档挑相关的问）

12. **里程碑顺序：** 哪一处最可能被人说"不对"？把它放最前面验。每个里程碑体验一遍不超过 10 分钟。
13. **失败场景：** 输入非法、网络失败、数据损坏时分别怎么处理？
14. **哪些参数该做成现场可调：** 主观的感受类参数不要靠描述来回改。
15. **验证手段：** 哪些能自动测？哪些必须人亲自体验？
16. **版权、合规、隐私：** 数据会不会离开本机？有没有素材授权问题？
17. **最大风险：** 你觉得最可能做不出来或做歪的是哪一块？先对它做小实验。

## 6. 工具 / 网站补充（web_app_tool）

- **使用场合：** 办公、个人、给别人用？一次用多久？
- **输入从哪来：** 粘贴、上传、手输？格式有哪些？非法输入怎么办？
- **输出给谁、怎么用：** 看一眼、复制、导出什么格式？
- **三种状态：** 加载中、空、出错，分别长什么样？
- **设备：** 桌面、手机宽度、两者？要不要离线可用？
- **数据量：** 几条还是几万条？要不要分页、搜索、筛选？
- **隐私：** 数据是否只在本机？是否需要登录？（推荐：本轮不做登录和云端）

## 7. 游戏补充

- **核心循环一句话，一局多长？**
- **先灰盒验手感：** 手感参数有哪些、F9 调参面板放哪？（见 `game-layer.md`）
- **存档、种子复现、确定性** 要不要？
- **类型预设里的"常见返工点"逐条确认哪些适用。**

## 8. 收尾检查（分支清空前逐条确认）

- [ ] 每条"必须做"都有对应的验收场景
- [ ] 每条"不做"都明确了，不会被悄悄加回来
- [ ] 数据来源、保存方式、演示数据标识都有结论
- [ ] DESIGN §6 的占位符都替换了（`check_docs.py` 在里程碑进入待验收前会拦这一条）
- [ ] 所有假设都标成"假设"，放在 §9
- [ ] 人明确说了"共识达成"

## 9. 反模式

- 一次抛出十几个问题：人没耐心，回答质量下降。按轮来。
- 问人能查到的事实：浪费人的注意力。
- 没有推荐答案：人要从零想，答得慢。
- 把假设当共识写进 DESIGN：后面返工的主要来源。
- 追问变成辩论：人说"就这样"就记下，不要反复确认。
