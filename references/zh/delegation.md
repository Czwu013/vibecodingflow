# 分派层：把合适的任务交给合适的模型

目录：1 为什么分派 · 2 路由准则 · 3 任务卡 · 4 并行 · 5 升级阶梯 · 6 记录与校准 · 7 反模式 · 8 平台说明

## 1. 为什么分派，以及什么时候不该分派

分派有两个好处：把大段执行过程挡在主会话之外（主会话只收到一份汇报，省上下文），以及让便宜的模型做它做得好的事（省成本）。

代价是每个子代理都是冷启动，要重新读项目上下文。任务太小，冷启动的开销比任务本身还大，这时候直接做更划算。所以分派不是越多越好，只分派"边界清楚、可以机器验证"的活。

## 2. 路由准则

**先过四问。** 一个任务要交给子代理，四个问题都要回答"是"：

1. 目标一句话说得清，不需要先做设计取舍？
2. 范围有界：文件范围列得出来，通常不超过三个文件？
3. 能机器验证：有命令、断言、截图对比可以判定通过与否？
4. 不涉及主观判断、跨模块架构、存档迁移？

任何一问是"否"，就留在主会话。

**路由表（起点，需要用你自己的数据校准，见第 6 节）：**

| 路由 | 适合的任务 | 对应子代理 |
| --- | --- | --- |
| 主 | 需求有歧义；解读主观反馈；归并反馈根因；架构和跨模块改动；写"请你重点判断"；DECISIONS；熔断后的换方案；一个新里程碑的第一个任务（它定下代码模式） | 主会话自己 |
| sonnet | 边界清楚的实现任务：按任务卡写一个功能、一个模块、一个带测试的修复；写冒烟脚本和截图；独立验证 | `dk-implementer`、`dk-verifier` |
| haiku | 纯机械的搬运：把面板文本写回验收卡、转录 feedback_log、更新索引日期、按人给的数字填配置、格式转换 | `dk-scribe` |
| opus | 独立审查：连续两轮没过后的根因分析；存档迁移等高风险改动；里程碑交付前的审计 | `dk-reviewer` |

**为什么主观反馈必须留在主会话：** 人说"有点飘"，要把它翻译成具体改动，既要理解 DESIGN 里的验收基准，又要对照 `taste.md` 和之前几轮的反馈。这是整个流程里最需要判断力的一步，分派出去只会让误解被放大。

## 3. 任务卡

交给子代理的简报，要自包含，因为它什么都不知道：

```
任务：<一句话目标>
计划：docs/dev/plans/Mx_xxx.md 的任务 T2
文件范围：src/player.js, src/config.js
必读：AGENTS.md；contracts/code_rules.md；taste.md 的 T-001
机器验证：npm test -- player（全部通过），并截图 evidence/M1/player.png
不要做：不改范围外文件；不改文档和里程碑状态
汇报：按 dk-implementer 的汇报格式
```

任务卡的内容来自计划文件的任务表。表里每一行就是一张任务卡的骨架。

## 4. 并行

- 文件范围互不重叠的任务可以并行，一次最多三个。有重叠就串行。`check_docs.py` 会对重叠的未完成委派任务发警告。
- 并行的子代理共用一个工作目录。有冲突风险时，让每个子代理在独立的 git 工作树里运行（Agent 工具支持 `isolation: "worktree"`），完成后由主会话合并。
- 验证者适合与实现者的下一个任务并行：实现者做 T3 时，验证者验 T2。

## 5. 升级阶梯

| 情况 | 动作 |
| --- | --- |
| 子代理汇报"通过" | 主会话抽查关键声明：高风险任务重跑一次验证命令；其余看汇报 |
| 第一次没通过 | 补充任务卡里缺的信息，重派。计划表"结果"记 `返修1次` |
| 第二次没通过 | 升一级：sonnet 换 opus，或主会话接手。结果记 `升级` |
| 主会话处理仍然不过 | 触发熔断，交 `dk-reviewer` 做根因分析，换方案 |

失败两次就升级的理由：同一个模型对同一张任务卡的第三次尝试，成功率不会因为多试一次而明显提高，更可能说明任务卡不清楚或任务超出了这个级别。

## 6. 记录与校准

计划文件的任务表里每行有两列：`路由`（主 / sonnet / haiku / opus）和`结果`（一次通过 / 返修1次 / 返修2次 / 升级）。`check_docs.py --stats` 会按路由统计：完成数、一次通过率、平均返修次数、升级率。

**怎么用这些数据（经验阈值，不是定论）：**

- 某个路由完成 ≥10 个任务后再看，数据太少没有意义。
- sonnet 一次通过率 <60%：任务卡可能写得不够清楚，或"四问"把得不够严，先收紧委派条件。
- sonnet 一次通过率 ≥90%：试着把更多任务下放，或把 haiku 用在更多机械活上。
- 升级率高的任务类型，下次直接留在主会话。

模型之间"什么任务该给谁"的官方指引并不存在，这张路由表是起点。**用你的项目数据决定，比用任何人的直觉都准。**

## 7. 反模式

- 把"把手感调好一点"丢给子代理：没有验收检查，也没有边界。
- 没有"机器验证"的任务也委派：你无法知道它做对没有。
- 一次派十个很小的任务：冷启动开销压过收益。合并成一个有边界的任务更好。
- 对汇报照单全收：高风险任务必须抽查。
- 让子代理改文档和状态：状态是主会话和人的事，子代理一改，"AI 不能自己宣布完成"就被绕过了。

## 8. 平台说明

- **Claude Code：** 子代理定义放在 `.claude/agents/`（`init.py --agents` 会拷贝）。每个定义的 `model` 字段指定默认模型，值可以是 `sonnet`、`opus`、`haiku`、`fable`、完整模型 ID 或 `inherit`。调用时也可以用 Agent 工具的 `model` 参数临时覆盖，优先级高于定义里的 `model`。主会话靠子代理的 `description` 判断何时委派。子代理定义的描述会计入启动时的 token 预算，所以这里只带 4 个，描述保持简短。
- **子代理不再往下派：** 这 4 个定义的 `tools` 白名单里都没有 Agent，避免多层嵌套。
- **claude.ai：** 没有子代理机制，主会话按任务卡自己执行即可，路由表仍然可以用来决定"哪些活值得多花注意力"。
- **Codex、Cursor 等：** 任务卡和任务表是通用的，可以手动把任务卡交给对应工具里的另一个会话。
