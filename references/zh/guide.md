# AI 协作开发文档框架 · 使用说明

适用于「人定方向和验收、AI 写代码」的项目（游戏、网站、工具都可以）。
核心思路：**AI 能完成 90%，最后 10% 是只有人能做的判断。把这 10% 做到又快又准，返工、修 bug、token 消耗都会少。**

具体落到两件事：

1. **让下一个接手的 AI，不用问你就知道该遵守什么、做到哪了、还欠什么。**
2. **让你的判断变成几分钟的点选：打分、标问题、一键复制，机器能直接读懂。**

## 一、七条原则

1. **意图和现实分开写。** 设计文档只写「打算做成什么样」；`CURRENT_STATE.md` 只写「代码现在实际是什么样」。两者不一致的地方记进 `known_mismatches.md`。
2. **重大决定留下理由。** 每个决定在 `DECISIONS.md` 写一条：改了什么、为什么、放弃了什么。推翻旧决定时写新条目，不删旧的。
3. **来不及就记账。** 文档没空更新、问题没空修，先在 `DEVELOP_DEBT.md` 记一笔，写清「怎样才算还清」。不记账的过期文档比没有文档更危险。
4. **一个入口管所有文档。** `docs/dev/README.md` 列出每份文档的用途、最后更新时间和状态（最新 / 待更新 / 归档）。过期的文档要么更新，要么移进 `archive/`。
5. **AI 不能自己宣布完成。** 状态流转：待做 → 进行中 → 待验收 → 完成。AI 最多标到「待验收」，并附上自测证据；只有人在验收卡上签字、结论为「通过」，才算「完成」。脚本会检查这一点。
6. **不让人做机器能做的事。** 能运行、无报错、关键路径冒烟，AI 交付前自己查。人的时间只花在手感、观感和取舍上。
7. **让人的判断便宜而准确。** 有统一的打分尺子，反馈有固定格式，主观意见尽量变成能拖动的参数。

## 二、每份文档的作用

| 文档 | 回答什么问题 | 谁写 | 什么时候更新 | 精简版必备 |
| --- | --- | --- | --- | --- |
| `README.md`（根目录） | 这是什么项目？怎么运行？怎么验收？ | AI | 运行方式变化时 | ✓ |
| `AGENTS.md` / `CLAUDE.md` | AI 打开项目第一眼该读什么？ | 人定，AI 维护 | 很少变 | ✓ |
| `docs/design/DESIGN.md` | 打算做成什么样？**4 分是什么样？**（GDD / 产品需求） | 人 + AI 讨论 | 设计变化时，先改这里再改代码 | ✓ |
| `docs/dev/README.md` | 所有文档的索引、状态流转、AI 开工顺序 | AI | 每次改任何文档时 | ✓ |
| `docs/dev/CURRENT_STATE.md` | 代码现在实际能做什么、关键实现在哪（≤100 行） | AI | 每个里程碑结束时 | ✓ |
| `docs/dev/DECISIONS.md` | 为什么是现在这样？当时放弃了什么？ | AI 记，人确认 | 每次重大决定 | ✓ |
| `docs/dev/DEVELOP_DEBT.md` | 还有什么没解决？怎样才算解决？ | AI | 发现欠账时、还清时 | ✓ |
| `docs/dev/known_mismatches.md` | 代码和设计哪里对不上？以哪边为准？ | AI | 发现偏差时 | ✓ |
| `docs/dev/feedback_log.md` | 你提的每个问题，现在到哪了？ | AI 根据验收卡记录 | 每轮验收后 | ✓ |
| `docs/dev/contracts/` | 写代码必须遵守的规则、反馈友好性要求、你的品味档案 | 人定，AI 补充 | 立新规矩时 | ✓ |
| `docs/dev/plans/` | 每个里程碑：做什么、怎么做、自测验证了什么（含截图证据） | AI | 每个里程碑 | ✓ |
| `docs/dev/reviews/` | **验收卡**：AI 的交付说明 + 你的打分与结论 + 验收面板 | AI 写前半，人填后半 | 每轮验收 | ✓ |
| `docs/dev/archive/` | 退役的文档（不删，留档） | AI | 文档过期时 | ✓（可空） |
| `docs/dev/audits/` | 代码审查记录 | AI 或第二个 AI | 定期或大改之后 | 需要时建 |
| `docs/dev/ledgers/` | 素材、内容、文案的逐项台账（来源、授权） | AI | 开始加素材时 | 游戏 / 需要时建 |
| `docs/dev/references/` | 外部资料、技术文档摘要 | AI | 查资料时 | 需要时建 |
| `docs/dev/roadmaps/` | 每个版本准备完成哪些目标 | 人 + AI | 规划新版本时 | 需要时建 |
| `docs/dev/bench/` | 性能测试方案、实测数据 | AI | 出现卡顿时 | 需要时建 |
| `docs/research/` | 竞品、对标、机制调研 | AI | 立项和设计阶段 | 需要时建 |
| `docs/release_notes/` | 每个发行版本更新了什么（给用户看） | AI 起草，人确认 | 每次发布 | 第一次发布时建 |

**精简版**（项目刚开始时用）：只建标 ✓ 的。其他等真正有内容时再建；空文件夹会让 AI 以为有东西要维护。

> 相比最初版本的变化：原来的 `checklists/`（验收清单）改为 `reviews/`（验收卡），把"流程 / 视觉 / 手感"的勾选升级为五维打分、结构化问题和可点选面板；`feedback_log` 增加维度和严重度；新增 `contracts/feedback_friendly.md` 和 `contracts/taste.md`。

## 三、一次完整的开发循环

1. **开工：** AI 读 `AGENTS.md` → `docs/dev/README.md` → `CURRENT_STATE.md` → `plans/README.md` → `contracts/`。
2. **先还高优先级的债：** 查 `DEVELOP_DEBT.md` 和 `feedback_log.md` 里的"高"。
3. **只做一个里程碑：** 在 `plans/` 写计划 → 写代码 → **自测**（运行、截图、冒烟、看报错）→ 证据放进 `plans/evidence/`。
4. **交付验收：** `new_review.py` 生成验收卡，AI 填好体验路线、已验证项、请你重点判断的问题；`build_panel.py` 生成点选面板；状态改为「待验收」。
5. **人验收（几分钟）：** 打开面板，跟着路线走，打分，标问题，点「复制给 AI」，粘贴回对话。
6. **AI 处理反馈：** 写回验收卡，问题进 `feedback_log`，按结论分流：
   - **通过** → 你已签字，标「完成」，git 提交存档；
   - **小改后过** → 合并改一批，下一轮你只复验改过的几条；
   - **返工** → 退回「进行中」，合并改一批；连续两轮返工就换方案。
7. **收尾：** 更新 `CURRENT_STATE.md`、`plans/`、`DECISIONS.md`（如有）、入口表；运行 `check_docs.py`。

## 四、立项时先问自己的批判性问题（写进设计文档开头）

1. 现在要做的东西，在不在最小可用版本里？
2. AI 能不能完整读懂、改动这个项目？（技术选型是否全在代码里，不依赖 AI 无法操作的图形编辑器）
3. 改坏了能不能一键退回？（git 或文件夹备份）
4. 这次是不是只改了一件事？
5. 报 bug 时信息够不够定位？（程序里能不能一键复制调试信息）
6. 新对话里的 AI 知不知道之前定过的规则？（→ 本框架）
7. 主观的手感 / 观感参数，能不能让人现场调？
8. 主题和新功能是否真的改变了用户的决策，还是只换了皮？
9. 有没有版权、合规、平台上架风险？

## 五、使用方法

1. 运行 `python scripts/init.py <项目目录> --name "<项目名>" [--game] [--full]`，或者直接让装了本 skill 的 Claude 帮你初始化。
2. 全局搜索 `{{`，把占位符换成你的项目内容；DESIGN 第 6 节「验收基准」务必认真写。
3. 用 AI 工具开工时，告诉它：「先读 AGENTS.md」。
4. 设计文档也可以放在线上（在线文档便于编辑和评论），这时把 `docs/design/DESIGN.md` 换成一行链接即可，**不要保留两份**。
5. 日常用 `python docs/dev/tools/check_docs.py` 检查；`--stats` 看返工趋势。

## 六、进阶能力

1. **类型验收基准预设。** `init.py --genre platformer` 之类，把"这一类游戏 4 分长什么样"、手感参数起点、常见返工点、体验路线示例直接带入项目。不用从零想尺子，首轮验收后再按口味校准。
2. **分派给子代理（Claude Code）。** 边界清楚、能机器验证的任务，交给 Sonnet / Haiku 子代理；解读你的主观反馈、状态、签字永远由主会话和你负责。路由写在计划的任务表里，统计会告诉你"哪类任务交给谁最划算"。详见 `delegation.md`。
3. **强制。** `init.py --hooks` 让"AI 不能自己宣布完成"不再靠 AI 自觉：收工时有 ERROR 会被拦住，提交时也会被拦；新会话自动看到状态摘要。
4. **接手已有项目。** `adopt.py` 扫描事实，AI 写出 CURRENT_STATE 和欠账草稿，所有推断标「待确认」，你在 M0 验收卡上签字确认。
